# Практическая №1 — Вариант 1 - Q3 «Shipping Priority»

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Седова Кристина Александровна |
| Вариант (запрос) | Q3 «Shipping Priority» |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | Изначально я планировала использовать масштаб sf0.1 — компромиссный вариант между скоростью и объёмом. Однако при выполнении `SHOW SCHEMAS FROM tpch` выяснилось, что коннектор TPC-H в Trino предоставляет только фиксированный набор схем: tiny, sf1, sf100, sf300, sf1000, sf3000, sf10000, sf30000, sf100000. Промежуточных масштабов (sf0.01, sf0.1, sf10) в списке нет. Из доступных вариантов tiny (~60 тыс. строк) слишком мал для статистически значимого бенчмарка сжатия — разница между кодеками утонула бы в погрешности. Ближайший подходящий — sf1. Он является стандартным масштабом TPC-H, широко используется в академических бенчмарках и даёт репрезентативные объёмы: 6 001 215 строк в lineitem, 1 500 000 заказов, 150 000 клиентов. Этого достаточно, чтобы бенчмарк сжатия показал осмысленные различия между кодеками. Более крупные масштабы (sf100+) не помещаются в разумные лимиты по диску и времени на локальном ноутбуке. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище, куда физически падают parquet-файлы Iceberg-таблиц | Open-source, бесплатный, полностью S3-совместимое API. Позволяет эмулировать AWS S3 локально без облачных затрат. Альтернатива (HDFS) тяжелее в настройке и не даёт S3-API, что ломает совместимость с Iceberg. Использован community-образ `netvark/minio`, поскольку официальные Docker-образы MinIO перешли на платную лицензию AIStor (при попытке скачать `quay.io/minio/minio` Docker возвращал 401 Unauthorized). |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога (список warehouse, namespace, таблиц, снапшотов) | Стандартная реляционная БД, поддерживается Lakekeeper из коробки. Лёгкая, надёжная, знакомый SQL. Альтернативы (MySQL, SQLite) либо хуже документированы для Lakekeeper, либо не подходят по нагрузке. |
| Lakekeeper | Iceberg REST Catalog — REST-каталог метаданных таблиц | Open-source реализация Iceberg REST Catalog на Rust. Совместим со стандартом Iceberg REST, работает с Trino/Spark без проприетарных зависимостей. Альтернатива — Nessie — тоже REST-каталог, но Lakekeeper легче в настройке и не требует Git-подобной модели данных. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет parquet в MinIO | Быстрый распределённый SQL-движок, имеет нативный Iceberg-коннектор и встроенный TPC-H-коннектор (что критично для генерации тестовых данных без скачивания). Альтернатива — Spark — тяжелее, требует JVM-настройки, и для аналитических запросов Trino работает быстрее за счёт in-memory-обработки. |
| Metabase | BI-инструмент для визуализации данных Bronze | Изначально я планировала использовать Apache Superset — он считается более мощным BI-инструментом и официально поддерживает Trino через SQLAlchemy. Однако при попытке развернуть Superset через официальный `docker-compose.yml` возникла ошибка `failed to read dockerfile: open Dockerfile: no such file or directory` — compose ожидал локальный Dockerfile. После перехода на `docker-compose-image-tag.yml` появилась другая ошибка: `exec: "/app/docker/docker-init.sh": stat /app/docker/docker-init.sh: no such file or directory` — в официальном образе отсутствует скрипт инициализации. Эти проблемы повторялись даже при указании стабильного тега `5.0.0`. В результате я переключилась на Metabase — он запускается одной командой `docker run` без сборки и сложной инициализации, имеет официальный драйвер Starburst (Trino) прямо в образе и работает стабильно. Для локальной лабораторной работы функциональности Metabase более чем достаточно. |

## 3. Разбор запроса — какие данные нужны

Запрос Q3 «Shipping Priority»: выручка по заказам сегмента BUILDING, которые надо отгрузить после 15 марта 1995, топ-10 по выручке.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает |
|---|---|---|
| customer | custkey, mktsegment | Фильтр `mktsegment = 'BUILDING'`, джойн с orders по `custkey` |
| orders | orderkey, custkey, orderdate, shippriority | Фильтр `orderdate < 1995-03-15`, джойн с customer по `custkey` и с lineitem по `orderkey`. `shippriority` выводится в результат |
| lineitem | orderkey, extendedprice, discount, shipdate | Фильтр `shipdate > 1995-03-15`, джойн с orders по `orderkey`. Агрегат `revenue = SUM(extendedprice * (1 - discount))` |

## 4. Медальон — решения по каждому слою

### Bronze (сырой)

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| tpch_customer | custkey, mktsegment | 150 000 | 0.6 | PARQUET | ZSTD | нет | Храним только нужные для Q3 колонки, чтобы не тратить место. ZSTD — дефолт Trino/Iceberg, лучший баланс сжатия и скорости. Партиционирование не нужно: таблица маленькая, фильтр по mktsegment даёт всего ~15% строк |
| tpch_orders | orderkey, custkey, orderdate, shippriority | 1 500 000 | 6.7 | PARQUET | ZSTD | нет | Колонки отфильтрованы по Q3. Партиционирование по orderdate не окупается на объёме 1.5 млн строк — накладные расходы на управление партициями превысят выигрыш |
| tpch_lineitem | orderkey, extendedprice, discount, shipdate | 6 001 215 | 38.6 | PARQUET | ZSTD | нет | Крупнейшая таблица. Партиционирование по shipdate потенциально полезно, но Q3 использует широкий диапазон дат (после 1995-03-15) — почти все данные попадут в одну-две партиции, эффект минимален. ZSTD экономит ~40% места относительно SNAPPY без потери скорости |

### Silver (очищенный)

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| order_lines | orderkey, orderdate, shippriority, extendedprice, discount, shipdate | 30 519 | 1.1 | PARQUET | ZSTD | нет | Уже отфильтрованные и объединённые данные: только заказы сегмента BUILDING с нужными датами. Все фильтры и джойны сделаны здесь, чтобы Gold работал по маленькой таблице. Партиционирование не нужно — таблица крошечная |

### Gold (витрина)

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| q3_shipping_priority | orderkey, revenue, orderdate, shippriority | 10 | < 0.1 | PARQUET | ZSTD | нет | Готовая витрина для бизнеса: топ-10 заказов по выручке. Крошечная таблица, любое партиционирование бессмысленно. Основное назначение — быстрый ответ на конкретный бизнес-вопрос без повторного выполнения тяжёлых джойнов |

## 5. Тесты производительности

Замер выполнялся по одному и тому же SQL-запросу Q3, но напрямую к Bronze-таблицам (`tpch_customer ⋈ tpch_orders ⋈ tpch_lineitem`). Кодек менялся через параметр `iceberg.compression-codec` в конфиге каталога `bronze.properties`, после чего Bronze-таблицы пересоздавались.

| Сжатие на Bronze | Время запроса, сек | Размер Bronze (lineitem / orders), МБ | Твой вывод |
|---|---|---|---|
| GZIP | 5.227 | 38.2 / 7.3 | GZIP даёт наименьший размер для крупной таблицы lineitem (38.2 МБ), но время запроса чуть выше, чем у ZSTD. На маленькой таблице orders GZIP сжал хуже, чем ZSTD (7.3 vs 6.7 МБ) — короткие строки GZIP сжимает неэффективно |
| ZSTD | 5.066 | 38.6 / 6.7 | ZSTD показывает лучшее время запроса (5.066 сек) и выигрывает по размеру на маленькой таблице. На крупной lineitem разница с GZIP в размере — менее 1% (38.6 vs 38.2 МБ). ZSTD — современный кодек, даёт лучший баланс скорости и сжатия, что подтверждается тем, что он используется как дефолт в Iceberg и Trino |

**Дополнительный замер:** тот же Q3, но по Silver-таблице `order_lines` (уже отфильтрованной) — **0.201 сек**. Ускорение относительно Bronze — примерно в **25 раз**. Это наглядно показывает смысл медальона: тяжёлые джойны и фильтры делаются один раз при построении Silver, а витрины Gold считаются быстро.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычные реляционные БД (PostgreSQL, MySQL) плохо масштабируются на петабайты: вертикальное масштабирование упирается в железо, шардирование сложное и дорогое. Data lake даёт дешёвое хранение в объектном хранилище, но не даёт транзакций, схемы и SQL. Lakehouse — компромисс: данные лежат в дешёвом S3 в открытых форматах (parquet), а сверху Iceberg даёт ACID-транзакции, schema evolution, time travel и полноценный SQL через Trino. Это позволяет и хранить дёшево, и анализировать быстро, и не терять данные при изменениях |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Iceberg хранит метаданные отдельно от данных, поэтому добавление колонки не требует перезаписи parquet-файлов — меняется только запись в метаданных таблицы. Старые строки при чтении получают `NULL` в новой колонке, новые строки — реальное значение. То же с переименованием: физические файлы остаются на месте, обновляется маппинг идентификаторов колонок. Это позволяет эволюционировать схему без downtime и без перезаписи петабайтов данных |
| Пример скрипта восстановления данных из снапшота (time travel) | В Iceberg каждая запись порождает новый снапшот. Посмотреть их и откатить можно так:<br>`SELECT * FROM "silver.lakehouse.order_lines$snapshots";`<br>Затем восстановить на конкретный снапшот:<br>`ALTER TABLE silver.lakehouse.order_lines EXECUTE rollback_to_snapshot(<snapshot_id>);`<br>Или прочитать данные на момент снапшота без отката:<br>`SELECT * FROM silver.lakehouse.order_lines FOR VERSION AS OF <snapshot_id>;` |

## 7. Выводы

В ходе работы я развернула локальный Lakehouse на стеке MinIO → Lakekeeper → Trino и построила медальонную архитектуру Bronze → Silver → Gold на данных TPC-H Q3 в масштабе sf1. Поняла, что медальон решает проблему постепенного «облагораживания» данных: Bronze хранит сырые данные, полученные напрямую из источника; Silver содержит очищенные и отфильтрованные данные (30 519 строк вместо 6 млн); Gold — готовые агрегаты для бизнеса. Бенчмарк сжатия показал, что ZSTD предпочтительнее GZIP: на нашем объёме он даёт то же сжатие при меньшем времени запроса, а также лучше работает на маленьких таблицах. Замер Q3 по Silver (0.2 сек) против Q3 по Bronze (5 сек) наглядно показал преимущество медальона — ускорение в 25 раз. Выбор Iceberg + MinIO позволяет хранить данные в дешёвом объектном хранилище и при этом работать с ними через полноценный SQL, что недоступно классическим data lake.
